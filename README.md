# Overwatch Map Affinity

Everybody knows that Overwatch heroes vary with their performance based on each map, and most can even name those cases, such as Winston being good at Watchpoint: Gibraltar. But still I wanted to see the extent of the map effect, and make a deep dive to find how each hero is effected by map changes. So, I pulled ranked win rate data and built something that answers it properly: for every hero, on every map, how much does their win rate move relative to their own average?

I didn't want to make a system that was dependant on patches, but rather wanted to find values that would stay the same regardless of hero's current balance or meta status, so I used "delta win rate" (map win rate minus the hero's baseline win rate for the same rank/region/patch slice). Of course this data is only valuable without any hero or map reworks, in those cases the data needs refreshing. But these values in this research should, in theory, survive regular balance changes.

## What's in here

- **`analysis/`** — the actual pipeline: collect the data, compute deltas, spit out a dataset and a markdown report.
- **`data/`** — `history/` is the frozen OWTics harvest of past seasons and `snapshots/` holds a daily snapshot of Blizzard's and Nexon's official stats from Season 5 on.
- **Live outputs, rebuilt daily** — the [full report](https://whenthiswinter.github.io/overwatch-map-affinity/report/) (every map's tier list, map sensitivity, the rank and region test), the CSVs for anyone who wants to have fun with it in a spreadsheet or notebook ([`map_tierlists.csv`](https://whenthiswinter.github.io/overwatch-map-affinity/data/csv/map_tierlists.csv), [`hero_volatility.csv`](https://whenthiswinter.github.io/overwatch-map-affinity/data/csv/hero_volatility.csv)), the charts below, and the site's dataset [`web_data.json`](https://whenthiswinter.github.io/overwatch-map-affinity/data/web_data.json). They're generated by the workflow and published on the site rather than committed, so they're always current.
- **`.github/workflows/daily.yml`** — runs the whole thing every day: collect, check for a new patch, rebuild, redeploy.
- **`web/`** — a small dashboard: filter by rank/region, look up a map or a hero, build a pool of your mains and export an offline cheat sheet. Tap any row for the details behind the number; the address bar keeps the current view, so links can be shared.

## The numbers

- **Delta WR** — a hero's win rate on a map minus their baseline win rate in that same rank/region/patch slice, averaged across every slice I collected (currently seasons 1-4 of 2026 including midseasons, Masters and up; season 5 is in progress, see *Provisional* below). It's a trimmed average: each pair's highest 30% and lowest 30% of slices are set aside first, because a few slices are wild (one put Lifeweaver at +43% on King's Row, where most sit near −2%). On held-out data this made the numbers much more reproducible (split-half correlation 0.52 → 0.72), and it uncovered real map effects the outliers had drowned out: Lifeweaver used to show the same value on every map. Tiers: S ≥ +3.0%, A +1.2 to +2.9%, B ±1.1%, C −1.3 to −3.0%, D < −3.0%.
- **Noise adjustment** — each average is made of slices that disagree with each other, so part of it is noise. Before tiering, every number is pulled toward the hero's overall mean in proportion to how noisy it is (empirical-Bayes shrinkage): a well-measured +5% stays near +5%, a +5% from a few inconsistent slices may end up near +1%. Without this, thin numbers land in S or D by chance; on narrow rank/region filters almost half the table used to. How strongly a number is pulled depends on the hero's map sensitivity (sigma, below). A single rank, region or the current patch alone is too thin to measure that, and used to flatten many heroes to the same value on every map, so it always comes from all ranks and regions; that predicted held-out data better on every filter tested. Tiers, archetypes and pool picks use the adjusted value; tap any row on the site to see the unadjusted average, and it's in the report and the CSV too.
- **Presence (pick rate lift)** — how much more or less often the hero is picked on the map than on their average map, in percent. Tells you whether a strong map is being drafted for, or slept on. It's relative on purpose: in absolute pick-rate points, popular heroes (Ana averages ~43%) got extreme labels about four times as often as rare ones (~3%), so the label mostly tracked popularity. *Map Priority* ≥ +50%, *Popular* ≥ +20%, *Standard* within ±20%, *Niche* ≤ −20%, placed at the same multiples of the typical lift (±33%) as the tier lines are of the typical win rate effect (2.1).
- **Archetype** — tier crossed with presence, with no cutoffs of its own: strong maps (A/S) are *Meta* if picked more than usual, *Specialist* if picked less, *Favorable* otherwise; weak maps (C/D) are *Trap Pick*, *Deterrent* or *Unfavorable* the same way; B is *Neutral*.
- **Why these lines** — the tier lines (±1.2 / ±3.0) were checked against how reproducible the labels are between independent halves of the data: they sit within 2% of the most informative split, with the most reliable individual labels of the near-optimal options (about 72% exactly right, 97% within one tier). Narrower bands would say slightly more overall but get individual labels right less often.
- **Sigma (map sensitivity)** — how much a hero's win rate really varies from map to map: the standard deviation of their map averages with the sampling noise subtracted. *Map-Agnostic* below 1.2 (most maps stay within the B band), *Map-Dependent* from 3.0 (a third or more of maps reach S or D). High sigma = map specialist, low sigma = plays about the same everywhere. It's measured on all ranks and regions and used for every filter. A hero's own data can't always pin it down: for Sierra and Venture the map differences are about the size of the noise, and the plain estimate used to come out as exactly 0, which flattened every map to the same value. So each hero's sigma is estimated together with all the others: where a hero's own evidence is strong (Widowmaker) it decides almost alone, and where it's weak the hero leans toward what's typical for heroes. Only win-rate data goes in, and the typical spread is fitted from the data, not chosen. On held-out data this predicted better for 35 of 51 heroes, and it puts Sierra and Venture at 0.8 and 1.0, in line with a separate check on the raw numbers. Heroes close to a class line are marked *borderline* when there's less than a 75% chance their true sigma is in the class shown (the same line as High confidence): about a dozen heroes sit near 1.2 or 3.0, where their own data can't say which side they're on.
- **Rank and region** — I originally flagged hero-map pairs whose delta differed by 2.5%+ between Masters and GM+, but a test showed those flags were noise, so they're gone. The test splits each pair's slices into two independent halves (season first halves vs midseasons): a real rank or region difference would show up in both halves, noise wouldn't. Between Masters and GM+ nothing repeats (split-half correlation −0.02 over 1,526 pairs), and no region differs from the others either. Europe came closest (+0.07) and first looked like a small real difference, but the p-value formula behind that was too optimistic: thin hero-map pairs are noisy in both halves, which makes chance correlations wider than the formula assumes. Simulating "no real difference" directly gives Europe p = 0.06, short of the bar. Even for GM+ or European numbers, the all-ranks/all-regions view predicts held-out data better than the narrower view, so it's the most reliable one. The test and its pass rule (one-sided p < 0.05 over all pairs, 0.0125 per region) were fixed in advance and are rerun every season ([`check_rank_region.py`](analysis/check_rank_region.py)); only the p-value calculation was corrected, against the one result it had found.
- **Provisional** — the patch currently in progress (a season or its midseason half) is left out of the averages for its first 21 days, because the first weeks of a patch are thin and noisy. Heroes and maps that only exist in the current patch (new releases and reworks, like Doctrine, Grímsvötn, and the reworked Sombra and Roadhog in Season 5) are still shown, built from current-patch data alone and marked *Provisional*. After 21 days the patch counts like any other. The site's *Data* filter can also show the current patch on its own.
- **Confidence** — the chance that the shown tier is right, from the same noise model as the adjustment: *High* ≥ 75%, *Medium* 50–74% (more likely right than wrong), *Low* < 50% (shown faded). Checked against held-out data, these probabilities are off by about 1 point on average on all ranks/regions, 2 on a single rank or region, and 4 on a single rank and region. A-tier labels are the least certain (narrow band), S and D the most. The unadjusted average's 95% range shows when you tap a row, and is in the report and the CSV.
- **Do the numbers behave like they should?** Three distribution checks on held-out data: the halves of the same pair differ exactly as much as the noise estimates predict (standardized spread 1.00 on all ranks/regions, 0.90–1.00 on every narrower filter, bell-shaped); real map effects are bell-shaped (the adjustment's one assumption); and the adjustment pulls by the right amount (slope 0.98).
- **Minimum sample size** — a hero-map pair needs at least 3 qualifying season/tier/region slices before it shows up anywhere. Below that, a single unlucky slice (a hero with barely any games on a map happens to lose all of them) can swing the average by 30-50 points and look like a real result when it's really just noise. Filtering down to a specific rank or region thins out the slices fast, so a hero that shows up on the all-ranks/all-regions view can disappear from a narrower one — that's the filter doing its job, not a bug. The one exception is a hero or map that just hasn't existed long enough to ever reach 3 slices under a narrow filter (a hero released this season, or a map reworked this season) — those show with whatever slices actually exist instead of getting hidden entirely, so a new hero isn't invisible on the site until they've been around for months.

## Running the site

The dashboard is static, it just fetches `data/web_data.json`. That file isn't checked in, so build it first, then serve the folder (browsers block the fetch over `file://`):

```bash
python analysis/build_dataset.py
python -m http.server 8000
```

Then open `http://localhost:8000/web/index.html`.

## How the data stays fresh

Blizzard (Americas, Europe, Asia) and Nexon (Korea) publish per-map win and pick rates for the current patch only, cumulative since the patch started. So a GitHub Action ([`daily.yml`](.github/workflows/daily.yml)) saves a snapshot of them every day:

1. `analysis/collect_live.py` saves the day's snapshot to `data/snapshots/`.
2. `analysis/detect_patch.py` checks whether the numbers reset, which happens on season and midseason patches. When they do, the old patch is frozen at its last snapshot and a new one starts, labelled from Blizzard's patch notes. Anything that needs a human (a new patch to check for reworks, a hero or map I don't know about yet) opens a GitHub issue.
3. `analysis/build_dataset.py` combines the frozen history with the newest snapshot of every patch. New heroes and maps are picked up from Blizzard's own listing automatically and shown as provisional.
4. Before anything goes live, the tests (`python -m unittest discover -s tests`) and a sanity check of the built dataset (`analysis/validate_dataset.py`) have to pass. If either fails, the site keeps its last good version and an issue is opened.

The same run also regenerates the report, CSVs and charts and publishes them with the site. Locally: `pip install -r requirements.txt`, then `python analysis/report.py`, `python analysis/charts.py` and `python analysis/render_report.py` (outputs land in `report/`, `charts/` and `data/csv/`, which git ignores).

Seasons 1-4 came from OWTics' API (`analysis/harvest.py`, which needs a `cf_clearance` cookie from a real browser session since OWTics sits behind Cloudflare) and were frozen into `data/history/` with `analysis/export_history.py`.

## Caveats

Heroes and maps added (or reworked) mid-timeframe are only counted from the season they were released or reworked in, so a rework starts that hero or map over from scratch (e.g. Sombra's move from Damage to Support in season 5).
